Say which Sentry, before a token finds out for you

`sentry` was one line of the generic bearer-token shape: `https://sentry.io/api/0`,
`/**` for reads and `/**` for writes, and nothing else true about Sentry
written down anywhere. Three things that shape cannot say, and all three fail
late.

**The region is part of the address.** Every sentry.io organization lives in
`us` or `de`, and an organization auth token carries its own region inside it.
Plain `sentry.io` routes to either, which is exactly why it is the wrong thing
to write into a policy file: it hides a mismatch until an agent hits it. The
profile takes `--var region=us|de` and writes the region host, so a wrong one
is a failed `verify` at enrolment rather than a 401 in somebody's logs. Both
Sentry profiles now also declare a probe — `/organizations/`, free on every
plan and every version, and a call a good-but-unentitled token answers with a
403, which `verify` reports as a warning rather than a failure.

**Self-hosted is the same API at your own host, and a different vintage.**
Sentry has shipped one version of this API — the `0` in `/api/0` — so
`sentry-self-hosted` is the same three levels behind `--var host=…`, with
`--var scheme=http` for an install that terminates TLS nowhere. What differs is
the release: self-hosted has been on calendar versions since 20.6.0, and an
endpoint your version predates 404s rather than being denied. The `triage`
rules name the project-scoped issue path alongside the organization-wide one
for that reason — a 9.x install has only the former, and a rule that knew just
the modern spelling would grant nothing there.

**`read` and `write` are not the two things an agent needs.** An agent watching
errors wants every read and exactly one write: the PUT that resolves, ignores
or assigns an issue. `write` would also let it edit projects, alert rules and
members, and that is not a trade anybody should have to take to get triage. So
there is a third level between them, DELETE denied outright rather than
prompted, and it is called `triage` on all four profiles.

Two of those four are the MCP server. `sentry-mcp` fronts the hosted one
directly: it offers OAuth first, but it also accepts `Sentry-Bearer <token>` in
the authorization header, so unlike the `cloudflare-mcp-*` profiles the
credential stays in the proxy instead of in a child process's cache.
`sentry-mcp-self-hosted` runs `@sentry/mcp-server` as a child pointed at your
host, with the token reaching it through `SENTRY_ACCESS_TOKEN` as the same
reference every other profile takes, and Seer disabled because self-hosted does
not have it. `analyze_issue_with_seer` is left out of the `read` level's allow
list on the hosted one too — it is the one read-shaped tool that spends, so it
lands on `ask` with the writes.

Tests: `triage` resolves an issue and cannot edit a project or delete
anything; the self-hosted profile reaches the older project-scoped issue path;
a plain-HTTP install is an explicit `--var`, not a default; the hosted MCP
enrols the `Sentry-Bearer` scheme and the self-hosted one passes a reference to
its child. The two catalog-wide tests now fill a variable from its declared
default where it has one, because `placeholder://host` is not a base URL any
proxy would load.
